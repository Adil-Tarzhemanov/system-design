Хорошая новость: ничего принципиально нового в этом уроке нет. FSD — это правило направления из урока 3, доведённое до готового свода соглашений, где у каждого этажа есть имя и заранее известно, кому что можно. Плохая новость: имён много, их путают, и на собеседовании это слышно сразу.

Зачем это на собесе

FSD сейчас спрашивают почти на каждом фронтовом собесе в СНГ — в Kaspi, Freedom, inDrive он встречается в вакансиях прямым текстом. Спрашивают три вещи: назови слои по порядку; сформулируй правила импортов; расскажи, за что FSD ругают. На третьем вопросе выигрывают: заученный ответ «FSD это круто» слабее честного «вот три места, где он мешает, и вот как мы их решали».

По ходу урока будут задания.

1. Что такое FSD и чем он не является

Определение самих авторов:

Feature-Sliced Design — архитектурная методология для проектирования фронтенд-приложений. Проще говоря, это свод правил и соглашений по организации кода.
Методология, а не архитектура — важное различие. Архитектура сказала бы «пусть будут фичи и общий слой». Методология идёт дальше: даёт конкретные имена, жёсткие правила, линтер-плагины и ответ на вопрос «а куда положить вот это».

Что FSD не является:

  • Не библиотека. Ставить нечего, это соглашение между людьми.
  • Не структура папок. Папки — следствие. Разложить файлы по правильным именам и нарушить все правила внутри можно за один вечер.
  • Не гарантия качества. «У нас FSD» — это про раскладку, а не про архитектуру. Помнишь вопрос из урока 1 про «у нас хорошая архитектура, мы используем RTK и FSD»?

2. Три оси деления — главная идея

Обычно код делят по одной оси: или по типам файлов (components/ hooks/ utils/), или по фичам (orders/ cart/). FSD делит по трём осям одновременно, и каждая отвечает на свой вопрос.

ОсьОтвечает на вопросИмена
СлойНасколько глобально это решение?Фиксированы: их ровно шесть
СлайсО чём это? Про заказ, про пользователя?Придумываешь сам, по своему домену
СегментЧто это технически — разметка, логика, запрос?Соглашение: ui, model, api, lib, config

  • Делит по области влияния, имён ровно шесть
  • Делит по предметной области, имена свои
  • Делит по техническому назначению внутри слайса
  • Единственная разрешённая дверь внутрь слайса
Задание 2

Внутри слайса features/add-to-cart лежат три файла. Какой из них попадёт в сегмент model?

  • AddToCartButton.tsx — кнопка с вёрсткой
  • useAddToCart.ts — состояние и логика добавления

Сегменты — соглашение, а не жёсткое правило: ui, model, api, плюс lib и config по необходимости. Заводить все пять в каждом слайсе не нужно — только те, что реально есть.

3. Шесть слоёв сверху вниз

Это ровно та лестница устойчивости из урока 3 — просто у этажей появились имена.

СлойЧто там живётПример
appЗапуск приложения: провайдеры, роутер, глобальные стили. Композиционный корень из урока 2app/providers/QueryProvider.tsx
pagesСтраницы целиком, по одной на слайс. Плоский список — по нему видно всё приложениеpages/checkout
widgetsСамодостаточный кусок интерфейса, который можно поставить на любую страницуwidgets/header, widgets/order-card
featuresДействия пользователя — юзкейсы. Обычно кнопка плюс логика за нейfeatures/add-to-cart
entitiesБизнес-сущности: то, над чем совершают действияentities/product, entities/user
sharedИнфраструктура: ui-кит, http-клиент, утилиты. Ни одного слова из доменаshared/ui/Button, shared/api/client
Мнемоника для порядка слоёв

Сверху вниз — от «что видит пользователь» к «из чего это сделано». Приложение → страница → блок на странице → действие → предмет действия → кирпичи. Если на собесе сбился, восстанавливай по этой цепочке, а не по заученному списку.

Куда положить компонент «карточка товара», который показывает картинку, название, цену и кнопку «в корзину»?

  • Целиком в features/add-to-cart
  • Разрезать: показ товара в entities, кнопку в features, сборку в widgets
  • В shared/ui, ведь карточка нужна на многих страницах
Приём сборки через слот — ровно тот, что был в уроке 2: сущность объявляет ReactNode, фича кладёт туда кнопку, виджет их соединяет.

4. Правило первое: импорты только вниз

Правило слоёв — модуль может импортировать только те слои, что лежат ниже его. Через слой вниз — можно. Вверх и вбок — нельзя.

Разрешено только движение вниз. Перепрыгивать через слой при этом можно — запрещено именно направление, а не расстояние.

Это то же самое правило направления из урока 3, только теперь этажи пронумерованы заранее. Вот как выглядит нарушение — пример из упражнения к этому уроку:

// widgets/header/ui.ts
import { PAGE_TITLE } from '../../pages/home/meta.ts';   // ← вверх: widgets тянет pages

export function renderHeader(): string {
  return `${upper(PAGE_TITLE)} · ${displayName()}`;
}
Почему это плохо — не «так принято»

Виджет шапки теперь перестал быть виджетом. Он больше не самодостаточный кусок интерфейса, а деталь главной страницы: поставь его на страницу заказа — и он покажет заголовок главной. Причём код при этом работает и тесты на поведение зелёные. Нарушение слоёв не ломает приложение сразу — оно ломает возможность переиспользовать, и выясняется это в проде.

Лечение всегда одно и то же: параметризация вместо похода наверх. Нижнему слою нужны данные из верхнего — он не идёт за ними, а принимает аргументом. Кто выше, тот и знает, что подставить.

// widgets/header/ui.ts — теперь виджет работает на любой странице
export function renderHeader(title: string): string {
  return `${upper(title)} · ${displayName()}`;
}

// pages/home/ui.ts — страница знает свой заголовок и передаёт его вниз
export function renderHome(): string {
  return renderHeader(PAGE_TITLE);
}
Задание 4

Какое из трёх нарушений опаснее остальных?

entities/user  →  features/auth      // сущность знает про фичу
shared/format  →  entities/user      // утилита знает про домен
widgets/header →  pages/home         // виджет знает про страницу
  • shared → entities: заражён самый нижний слой
  • widgets → pages: виджет перестал быть виджетом
  • entities → features: сущность знает про действие
Критерий тот же, что в уроке 3: чем ниже слой, тем дороже в нём нарушение — потому что тем больше на него завязано.

5. Правило второе: запрет кросс-импортов

Кросс-импорт — импорт между двумя слайсами одного слоя: features/cart тянет features/checkout. Запрещён.

Правило кажется избыточным — но именно оно не даёт слою превратиться в кашу. Если слайсы могут звать друг друга, через полгода features — это один большой комок, из которого нельзя вынуть ни одну фичу.

Что делать, когда фичам всё-таки надо общаться — три выхода, в порядке предпочтения:

  1. Поднять сборку наверх — соединить их в widgets или на странице. Приём номер один из урока 3.
  2. Опустить общее вниз — если обе фичи нуждаются в одном и том же знании, это знание про сущность, и место ему в entities.
  3. Слот или колбэк — фича объявляет ReactNode или onDone, а кто их заполнит, решает слой выше. Инверсия из урока 2.

После успешного features/login надо очистить features/cart. Прямой импорт запрещён. Как правильно?

  • login объявляет onSuccess, а страница вызывает в нём очистку
  • Объединить обе фичи в одну features/auth-and-cart

6. Правило третье: публичный API слайса

У каждого слайса есть index.ts — единственная разрешённая дверь. Снаружи импортируют только из него, внутренности недоступны.

// ✅ entities/product/index.ts — сознательно выбранная витрина
export { ProductCard } from './ui/ProductCard';
export { useProduct } from './model/useProduct';
export type { Product } from './model/types';

// ✅ снаружи
import { ProductCard } from '@/entities/product';

// ❌ снаружи
import { ProductCard } from '@/entities/product/ui/ProductCard';

Это дословно тот же публичный API из урока 1. И та же ловушка:

Ловушка из урока 1, которая жива и здесь

export * from './model' в index.ts — это не публичный API. Формально дверь есть, фактически стена стеклянная: наружу утекает всё, и через полгода на внутреннюю деталь кто-нибудь обязательно завяжется. Публичный API — то, что ты решил показать, а не то, что забыл спрятать.

Вспомни, не подглядывая

Назови все три правила FSD — своими словами, без подсказки.

1. Импорты идут только вниз по слоям: нижний слой не знает о верхних. 2. Слайсы одного слоя не импортируют друг друга — никаких кросс-импортов. 3. Внутрь слайса ходят только через его публичный API — index.ts.

7. За что FSD ругают — честно

Это тот самый третий вопрос, на котором выигрывают собеседование. Претензии реальные, и делать вид, что их нет, — худшая стратегия.

ПретензияНасколько справедлива
Shared превращается в свалкуПолностью справедлива. Это самое частое место, где FSD-проект гниёт: туда сваливают всё, что «не подошло никуда ещё»
Спор «фича или сущность» на каждом ревьюСправедлива. Граница между features и entities — вопрос вкуса, и команда тратит на него реальное время
Много бойлерплейтаСправедлива. Одна кнопка — папка, сегмент, index.ts. На маленьком проекте это чистый оверхед
Кросс-импорты между фичами лезут постоянноСправедлива, и это главный источник боли. Реальные фичи связаны сильнее, чем предполагает методология
«FSD — это оверинжиниринг»Справедлива для маленьких проектов и несправедлива для больших. Вопрос размера команды и срока жизни, а не вкуса
Как отвечать на «что вам не нравится в FSD»

«Больше всего мешал запрет кросс-импортов: реальные фичи связаны сильнее, чем предполагает методология, и половина задач упиралась в вопрос, куда поднять связь. Решали слотами и подъёмом сборки в виджет. Второе — shared: он расползается, если не завести явное правило. У нас правило было такое: в shared не должно встречаться ни одного слова из предметной области, и это проверялось на ревью.»

Задание 6

Интервьюер: «а зачем вам FSD, если можно просто делить по фичам?» Какой ответ сильнее?

  • «FSD — стандарт, его сейчас используют все»
  • «Даёт одинаковые имена и проверяемое правило импортов — новый человек знает, где что, а линтер ловит нарушения. Платим бойлерплейтом»
  • «Деление по фичам не работает, там всегда получается каша»

8. Что FSD реально решает

Если убрать маркетинг, остаются три вещи — и все три про людей, а не про код:

  • Одинаковые имена. Новый человек в команде уже знает, что такое entities и где искать запросы. Знание переезжает из «проектного» в «общеотраслевое» — это реально ускоряет онбординг.
  • Правило, которое можно проверить машиной. Направление импортов проверяется линтером в CI. Договорённость, которую нельзя проверить, не соблюдается.
  • Структура кричит о продукте. Открыл pages/ — увидел всё приложение. Открыл features/ — увидел, что пользователь умеет делать.

9. Как это звучит на собеседовании

Скрипт на 60 секунд

«FSD — не библиотека, а свод соглашений. Делит код по трём осям: слой — по области влияния, слайс — по предметной области, сегмент — по техническому назначению. Слоёв шесть, сверху вниз: app, pages, widgets, features, entities, shared. Три правила: импорты только вниз, слайсы одного слоя друг друга не импортируют, внутрь слайса — только через публичный API. По сути это принцип устойчивых зависимостей с готовыми именами: внизу то, что меняется реже, и там нет ни слова про наш домен. Что мешало — запрет кросс-импортов и разрастание shared; решали слотами и явным правилом на ревью.»

Чего не делать
  • Не путать слайс и сегмент. Слайс — cart, сегмент — ui.
  • Не называть FSD архитектурой. Это методология: правила плюс тулинг.
  • Не отвечать «у нас FSD» на вопрос про архитектуру проекта. Это раскладка файлов, а не решения.
  • Не хвалить FSD без единой претензии. Идеальных методологий не бывает, и интервьюер это знает.
  • Не оправдывать правила словами «так в документации». Называй эффект: что ломается без правила.

Шпаргалка

  • FSD — методология, свод правил. Не библиотека, не структура папок, не гарантия качества.
  • Три оси: слой (область влияния) · слайс (предметная область) · сегмент (техническое назначение).
  • Шесть слоёв сверху вниз: app · pages · widgets · features · entities · shared.
  • Мнемоника: от «что видит пользователь» к «из чего это сделано».
  • Правило 1: импорты только вниз. Через слой вниз можно, вверх и вбок — нет.
  • Правило 2: нет кросс-импортов между слайсами одного слоя.
  • Правило 3: внутрь слайса — только через index.ts. export * не считается.
  • Лечение похода наверх — параметризация: не идти за данными, а принять их аргументом.
  • Лечение кросс-импорта: поднять сборку наверх · опустить общее в entities · слот или колбэк.
  • Чем ниже слой, тем дороже нарушение. Самое опасное — домен в shared.
  • Нарушение слоёв не ломает код сразу — оно ломает переиспользуемость, и это всплывает в проде.
  • Претензии: свалка в shared · спор «фича или сущность» · бойлерплейт · кросс-импорты · оверхед на малых проектах.
  • Что реально даёт: одинаковые имена · правило, проверяемое линтером · структура кричит о продукте.
