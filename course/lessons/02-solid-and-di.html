Второй урок — про то, как модуль перестаёт зависеть от того, кого он вызывает. Тема выглядит академической («SOLID, интерфейсы, DI-контейнеры»), но именно она объясняет, почему в FSD работают слоты, почему onClick — это архитектурный приём, и почему на вопрос «в чём разница между dependency inversion и dependency injection» сыплется большинство кандидатов.

Зачем это на собесе

Два вопроса встречаются почти дословно: «расскажи про SOLID» и «чем инверсия зависимостей отличается от внедрения». На первом ждут не пересказ пяти букв, а то, что ты отличишь применимое от карго-культа. На втором отсеивают тех, кто выучил определения, но не может показать инверсию в обычном React-компоненте. К концу урока ты сможешь и то, и другое — и увидишь, что делал инверсию каждый день, не зная названия.

1. SOLID: почему его нельзя переносить дословно

SOLID сформулирован Робертом Мартином на рубеже 2000-х для языков с классами, наследованием и явными интерфейсами — Java, C#. Во фронтенде на React у нас функции, композиция и структурная типизация. Дословный перенос даёт карго-культ: абстрактные фабрики там, где хватило бы функции, и «интерфейс на каждый чих».

Но выкидывать SOLID тоже нельзя: три принципа из пяти во фронте работают отлично, если читать их не как правила про классы, а как правила про границы модулей — то есть ровно про то, о чём был первый урок.

Как звучит плохой ответ

«S — single responsibility, класс должен делать одну вещь. O — open-closed, открыт для расширения, закрыт для изменения. L — Лисков…» — заученный список без единого примера из своего кода. Интервьюер слышит это по десять раз в неделю и ставит галочку «читал статью».

2. Три принципа, которые работают во фронте

SRP — одна причина для изменения

Формулировка «модуль должен делать одну вещь» бесполезна: «одна вещь» — понятие резиновое. Рабочая формулировка Мартина другая:

У модуля должна быть ровно одна причина для изменения — то есть ровно один заказчик, чьи требования этот модуль обслуживает.

Критерий не «сколько делает», а сколько разных людей могут прийти с правкой.

// features/order-card — сколько заказчиков у этого файла?
function OrderCard({ order }) {
  const money = new Intl.NumberFormat('kk-KZ', { ... }).format(order.total); // финансы
  const canRefund = user.roles.includes('admin') || order.age < 14;          // безопасность
  const { data } = useQuery(['order', order.id], () => api.get(...));        // бэкенд
  return ...;                                                                // дизайн
}

Четыре независимых источника требований в одном файле. Смена формата денег, смена правил возврата, смена контракта API и редизайн — четыре разные команды будут править один и тот же файл и мешать друг другу. Это ровно та самая низкая cohesion из первого урока, только названная со стороны организации, а не со стороны кода.

OCP — расширяем, не изменяя

В ООП это про наследование. В React — про слоты и пропсы.

// ❌ каждый новый случай = правка самого Modal
<Modal mode="edit" | "view" | "compact" | "danger" />

// ✅ Modal не меняется никогда, меняется то, что в него кладут
<Modal header={<EditTitle />} footer={<SaveButton />}>{form}</Modal>

Первый вариант — это ещё и control coupling из таблицы первого урока: снаружи флагом управляют ветвлением внутри. Второй — data coupling: наружу отдан контракт, а не рычаг.

DIP — зависеть от абстракции, а не от реализации

Самый ценный из пяти и самый недопонятый. Ему посвящён весь остаток урока.

А что с L и I

Их спрашивают редко, но иметь по одной честной фразе на каждый стоит.

ПринципЧто говорить
LSP (Лисков)Без наследования во фронте почти не встречается. Живёт как правило «не ломай контракт при расширении»: если <IconButton> обёртка над <Button>, она обязана принимать всё, что принимал Button, и вести себя так же.
ISP (разделение интерфейсов)Не заставляй потребителя знать о том, чем он не пользуется. Во фронте это толстые пропсы (user целиком там, где нужен userId) и толстые контексты, из-за которых компонент ререндерится на чужие изменения.

3. Три термина, которые все путают

Это ядро урока. Разложи их один раз — и вопрос на собесе перестанет быть страшным.

ТерминЧто этоПример
DIP
Dependency Inversion Principle		 Принцип из SOLID: модули верхнего уровня не должны зависеть от нижних, оба зависят от абстракций. Пункт в чеклисте ревью
Dependency Inversion
инверсия зависимости		 Приём: развернуть стрелку зависимости в обратную сторону относительно вызова. Модуль объявляет нужный ему тип, реализация подстраивается
Dependency Injection
внедрение зависимости		 Механизм доставки: как конкретная реализация попадает внутрь. Аргумент функции, проп, React Context, DI-контейнер в Angular/NestJS
Формулировка, которую стоит запомнить дословно

«Инверсия зависимости — это когда поток управления не совпадает с потоком зависимостей. Инъекция — это просто способ доставить реализацию внутрь. Инверсия отвечает на вопрос кто кого знает, инъекция — на вопрос как передали.»

  • Поток управления (control flow) — кто кого вызывает.
  • Поток зависимостей (dependency flow) — кто кого импортирует, чей тип знает.

По умолчанию они совпадают: чтобы вызвать — надо импортировать. Инверсия — это когда их развели: вызов идёт вперёд, а знание — назад.

Инъекция без инверсии — возможна и бесполезна

Это главная ловушка вопроса. Смотри:

import type { TelegramClient } from '@/shared/telegram';

export function notify(client: TelegramClient, text: string) { ... }

Зависимость «внедрена» — её передали аргументом. Но тип пришёл из чужого модуля. Стрелка не развернулась, она просто переехала из import в сигнатуру: поменяется телеграм — поменяется и этот файл. Injection есть, inversion нет.

4. Фасад — это ещё не инверсия

Самое частое возражение: «у нас всё завёрнуто в сервисы, у нас уже абстракция». Разберём, почему этого мало.

userStore  →  userApi  →  httpClient
           (фасад)

userStore действительно не знает про httpClient напрямую — и это лучше, чем ничего: фасад скрывает изменчивость и даёт место для адаптации. Но:

  • зависимость осталась, просто стала транзитивной — изменение всё равно просачивается вверх по цепочке;
  • подменить реализацию можно только статически, переписав userApi;
  • userStore нельзя физически вынуть из проекта и переиспользовать — он тянет за собой весь хвост.
Детектор инверсии: кто владеет типом

Один вопрос, который отвечает на всё: где объявлен тип зависимости?

  • Тип объявлен в модуле-потребителе, реализация подставляется снаружи — инверсия есть.
  • Тип импортирован из модуля-реализации — инверсии нет, как бы красиво ни назывался слой.

5. Инверсия в TypeScript — без классов и без implements

В книжках инверсию показывают на интерфейсах и implements. В TS это чаще всего лишний ритуал: благодаря структурной типизации ничего не нужно явно имплементировать — достаточно совпадения по форме.

Было — checkout прибит к платёжному провайдеру:

// ❌ features/checkout/model.ts
import { stripe } from '@/shared/api/stripe';

export async function pay(orderId: string, amount: number) {
  const res = await stripe.charge({ order: orderId, sum: amount, cur: 'KZT' });
  return res.ok;
}

Стало — checkout объявляет, что ему нужно, и больше ни о чём не знает:

// ✅ features/checkout/model.ts — ноль импортов из чужих модулей
export type PaymentGateway = {
  charge(input: { orderId: string; amount: number }): Promise<{ ok: boolean }>;
};

export function createCheckout({ gateway }: { gateway: PaymentGateway }) {
  return {
    pay: (orderId: string, amount: number) => gateway.charge({ orderId, amount }),
  };
}
// app/composition.ts — единственное место, где живёт конкретика
import { createCheckout } from '@/features/checkout';
import { stripe } from '@/shared/api/stripe';

export const checkout = createCheckout({
  gateway: {                                    // ← это и есть адаптер, целиком
    charge: ({ orderId, amount }) =>
      stripe.charge({ order: orderId, sum: amount, cur: 'KZT' }),
  },
});

Ни одного class, ни одного implements. Адаптер — стрелочная функция, переименовывающая пару полей. Проверка совместимости произошла в момент подстановки: подошло по структуре — компилируется, не подошло — красное.

Побочный эффект, который стоит назвать вслух

Тесты. createCheckout({ gateway: fakeGateway }) — юнит-тест без единого мока, без jest.mock, без перехвата сети. Если на собесе спрашивают «как вы тестируете бизнес-логику», ответ «она не знает, откуда приходят данные, поэтому мокать нечего» сильнее любого рассказа про MSW.

Мелочь про type vs interface

Ключевое слово interface имеет смысл, когда есть класс с implements. Если классов нет — пиши type. Это передаёт намерение: type описывает форму, interface — контракт, который кто-то обязан реализовать.

6. Инверсия в React, которой ты пользуешься каждый день

А теперь неожиданное: половину приёмов из этого урока ты применяешь ежедневно, просто они не назывались этим словом.

ПриёмКто кого вызываетКто от кого зависит
onClick и любой колбэк-пропкнопка вызывает обработчиккнопка не знает о нём ничего
Слот: children или проп типа ReactNodeкарточка рендерит кнопку удалениякарточка не импортирует кнопку
Render propсписок рендерит элементсписок не знает тип элемента
Contextхук вызывает реализациюхук знает только тип контекста
// ❌ TaskCard знает про кнопку, кнопка знает про стор, стор знает про API
function TaskCard({ task }) {
  return <div>{task.title}<DeleteTaskButton id={task.id} /></div>;
}

// ✅ TaskCard не зависит ни на что, кроме своих пропсов
function TaskCard({ task, actions }: { task: Task; actions?: ReactNode }) {
  return <div>{task.title}{actions}</div>;
}

// собирается наверху, в композиционном компоненте
<TaskCard task={task} actions={<DeleteButton onClick={() => remove(task.id)} />} />

Обрати внимание на второй эффект: дерево стало плоским. Вместо лесенки App → TaskList → TaskCard → DeleteButton → store получилось четыре независимых компонента и один сборщик над ними. Глубина вложенности — хороший косвенный индикатор зацепления: чем глубже, тем больше компонент знает о том, что внутри него.

Готовый ответ на «приведи пример инверсии в React»

«Слот. Карточка задачи рендерит кнопку удаления, но не импортирует её — принимает ReactNode пропом. Поток управления идёт от карточки к кнопке, а зависимости от карточки к кнопке нет вообще: собирает их виджет уровнем выше. Это же объясняет, почему в FSD сущность объявляет слот, а фича кладёт в него кнопку — иначе сущность зависела бы от фичи, а это запрещённое направление.»

7. Context: когда это DI, а когда глобальная переменная

React Context — не стейт-менеджер. По назначению это механизм доставки зависимости: способ использовать абстракцию до того, как где-то в корне подставили реализацию. Именно так устроены все инфраструктурные библиотеки:

  • useQuery зависит от абстрактного QueryClient, конкретный передаётся в <QueryClientProvider> в app;
  • useNavigate не знает, history-роутер это, hash или memory;
  • useSelector не знает, из каких редьюсеров собран стор.

Это инверсия — но обрати внимание, в чью пользу: библиотека защищена от твоего кода, а не твой код от библиотеки.

Где контекст перестаёт быть DI

Если контекст объявлен рядом со своей реализацией и хранит её тип — это уже не инверсия, а глобальная переменная с ограниченной областью видимости. Признак тот же, что в разделе 4: тип пришёл со стороны реализации, а не со стороны потребителя. Такой контекст повышает coupling: все потребители завязаны на конкретный модуль, просто связь стала неявной. Лучше честный проп, чем контекст-невидимка.

Отсюда же ответ на вопрос «а контекст — это не сервис-локатор ли, который антипаттерн?». Нет, и вот почему: сервис-локатор императивен — все зависимости надо зарегистрировать до первого обращения, и при ленивой загрузке модуль может не успеть появиться. Контекст декларативен: не обёрнут в провайдер — падает сразу, явно и в предсказуемом месте. Плюс контекстов может быть много и каждый объявляет только свои зависимости, а локатор один на приложение.

8. Композиционный корень

У всех примеров выше есть общее: конкретика откуда-то исчезла из модулей — значит, куда-то приехала. Это место называется composition root: app/, main.tsx, провайдеры, composition.ts.

Composition root — единственное место в приложении, где абстрактное встречается с конкретным.

Он обязан быть «жирным» и зависеть от всех — это его работа, а не запах. Правило движения: конкретика течёт вверх, абстракции — вниз. А признак здоровой системы — у самых ценных модулей вообще нет импортов из соседних модулей.

9. Чем за это платят

Как и в первом уроке: любое решение — сделка, и обе стороны надо уметь назвать.

УдешевляемПлатим
Замену реализации: платёжка, транспорт, хранилищеКосвенность: чтобы понять, что реально вызовется, надо идти в composition root
Юнит-тесты без моков и перехвата сетиБольше кода: тип, фабрика, адаптер вместо одного импорта
Переиспользование и физический вынос модуля«Go to definition» ведёт в тип, а не в реализацию
Разрыв запрещённых связей в FSD без хаковПорог входа для новых людей в команде
Когда инвертировать НЕ надо
  • Чистые утилиты. formatDate, clamp, cn — у них нет изменчивости, инвертировать нечего.
  • Одна реализация, и она не меняется. Инверсия «на будущее» — это ставка на угаданное будущее, а первый урок был ровно о том, что угадывать не надо.
  • Внутри одного модуля. Инверсия — инструмент для границ, а не для внутренностей.

Рабочее правило: инвертируй там, где начинается чужая изменчивость — сеть, хранилище, платежи, аналитика, время и Math.random, а также любая запрещённая по слоям связь.

10. Как это звучит на собеседовании

Скрипт на 40 секунд

«Инъекция — это как передали: аргументом, пропом, через контекст. Инверсия — это кто кого знает: тип зависимости объявляет тот, кто её использует, а реализация подстраивается под него и подставляется в композиционном корне. Проверить легко: если тип импортирован из модуля-реализации — инверсии нет, сколько бы слоёв ты ни построил. В React это обычно даже не требует интерфейсов: слот, render prop и колбэк-проп — уже инверсия, потому что вызов идёт вниз, а зависимости вниз нет.»

Чего не делать
  • Не говорить «мы используем DI» про то, что просто принимает аргументы. Уточняй, чей тип.
  • Не называть фасад инверсией. Транзитивная зависимость никуда не делась.
  • Не предлагать DI-контейнер в React-проекте без крайне веской причины — это решение для мира, где всё построено на классах и интерфейсах.
  • Не отвечать на «расскажи SOLID» пересказом пяти букв. Назови, какие три работают во фронте и как они выглядят в компонентах.

Шпаргалка

  • SOLID во фронте: рабочие — SRP, OCP, DIP. LSP и ISP — по одной честной фразе.
  • SRP = одна причина для изменения = один заказчик правок, а не «делает одну вещь».
  • OCP в React = слоты и пропсы вместо флагов режима.
  • Инверсия = поток управления не совпадает с потоком зависимостей.
  • Инъекция = механизм доставки: аргумент, проп, контекст, контейнер.
  • Injection без inversion возможен и бесполезен: передал аргументом чужой тип — остался привязан.
  • Детектор: где объявлен тип зависимости? У потребителя — инверсия есть. У реализации — нет.
  • Фасад ≠ инверсия: остаётся транзитивная зависимость, подмена только статическая.
  • В TS не нужен implements — хватает структурной типизации, адаптер часто в одну стрелку.
  • Слот, render prop, колбэк-проп — инверсия, которой ты пользуешься каждый день.
  • Context — механизм доставки зависимости, не стейт-менеджер. Реализация рядом с контекстом — это глобальная переменная.
  • Composition root — единственное место встречи абстрактного и конкретного. Конкретика течёт вверх.
  • Не инвертируй чистые утилиты, единственную стабильную реализацию и внутренности модуля.

Первоисточник

  • Kent C. Dodds, «Inversion of Control» — kentcdodds.com/blog/inversion-of-control. Лучший разбор темы именно для React-разработчика: одна и та же функция рефакторится через инверсию шаг за шагом. Двадцать минут чтения.
  • Robert C. Martin, «Clean Architecture», главы 8 и 11 — первоисточник формулировок OCP и DIP, включая «поток управления против потока зависимостей».
  • Урок 2 курса Паромова (docs/paromov-lessons/2.md) — та же тема с примерами на классах, функциях, контексте и компонентах.
