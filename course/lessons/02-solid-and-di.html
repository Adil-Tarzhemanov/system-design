Этот урок — про одну идею: как сделать так, чтобы твой код не ломался, когда меняется чужой. У идеи есть пугающее имя «инверсия зависимостей», несколько похожих терминов, которые все путают, и буква D в аббревиатуре SOLID. Разберём по шагам, без единого слова без объяснения.

Зачем это на собесе

Два вопроса встречаются почти дословно: «расскажи про SOLID» и «чем инверсия зависимостей отличается от внедрения». Второй — фильтр: на нём видно, кто выучил определения, а кто понимает, что происходит в коде. К концу урока ты сможешь ответить на оба и увидишь, что делал инверсию каждый день, просто не знал названия.

По ходу урока будут задания.

Словарь урока

Все слова, которые дальше встретятся. Пока просто прочитай — каждое разберём на примерах, сюда можно возвращаться.

1. Зависимость: с чего вообще проблема

Зависимость — чужой код, без которого мой не работает. Если я написал import, я стал зависимым: чужие изменения теперь мои проблемы. 
// features/checkout/model.ts — мой модуль
import { stripe } from '@/shared/api/stripe';   // ← вот она, зависимость

export async function pay(orderId, amount) {
  const res = await stripe.charge({ order: orderId, sum: amount, cur: 'KZT' });
  return res.ok;
}

Обычная ситуация: обе стрелки идут в одну сторону. Я и знаю про stripe, и вызываю его.

Что с этим не так — три конкретные вещи:

  • Stripe поменяет формат — переименует sum в amount — и мне придётся править свой файл, хотя моя логика оплаты не изменилась ни на грамм.
  • Продукт скажет «добавляем Kaspi Pay» — придётся лезть внутрь checkout и городить там if.
  • Тест этой функции реально пойдёт в сеть. Чтобы не пошёл, нужны моки — подмена модуля на лету, отдельная библиотека, отдельная боль.
Вспомни, не подглядывая

Своими словами: что такое зависимость и по какому признаку её видно в файле?

Зависимость — чужой код, без которого мой не работает. В файле её видно по import: если я импортирую модуль, я знаю о его существовании и завишу от его формы.

2. Контракт — главное слово урока

Контракт — описание формы зависимости, без её содержимого. «Мне нужна функция, которая принимает вот такой объект и возвращает вот такой». Кто именно её выполнит — не моё дело.

Житейская аналогия: розетка. Розетка не знает, что́ ты в неё воткнёшь — чайник, ноутбук или зарядку. Она задаёт только форму: два отверстия, 220 вольт. Всё, что подходит по форме, работает. Розетка не зависит от чайника — это чайник обязан подойти под розетку.

Контракт объявляет тот, кому нужна помощь. Подстраиваются — те, кто её оказывает.

В TypeScript контракт пишется одной строкой — это обычный type:

// «мне нужен кто-то, кто умеет списывать деньги вот так»
export type PaymentGateway = {
  charge(input: { orderId: string; amount: number }): Promise<{ ok: boolean }>;
};

Здесь нет ни строчки рабочего кода — ни запроса, ни ключей, ни обработки ошибок. Только форма. Это и есть абстракция: сказано что, не сказано как.

Задание 1

Что из этого — контракт, а не реализация?

  • type Storage = { get(k: string): string | null }
  • const storage = { get: (k) => localStorage.getItem(k) }
  • const get = (k) => fetch('/api/' + k).then(r => r.json())

3. Две стрелки: кто вызывает и кто знает

Дальше всё держится на одном различении. Между двумя модулями всегда есть две разные стрелки, и их обычно не замечают, потому что они совпадают.

Поток управления (control flow) — кто кого вызывает. Кто первый начал работу, кому передал.
Поток зависимостей (dependency flow) — кто про кого знает. Кто кого импортирует, чьё имя и чью форму упоминает у себя в коде.

По умолчанию они смотрят в одну сторону: чтобы кого-то вызвать, надо его импортировать. Именно так было в примере из первого раздела. И вот вопрос, ради которого весь урок: а обязательно ли они должны совпадать?

Задание 2

Кнопка вызывает переданный ей onClick. Куда смотрят стрелки?

function DeleteButton({ onClick }) {
  return <button onClick={onClick}>Удалить</button>;
}
  • Управление — от кнопки наружу, зависимости от кнопки наружу нет
  • Обе стрелки от кнопки к обработчику, как обычно
  • Кнопка ничего не вызывает, она только рисует разметку
Ты только что опознал инверсию зависимости в четырёх строчках обычного React. Дальше просто дадим этому имя.

4. Инверсия — развернуть стрелку знания

Инверсия зависимости — ситуация, когда поток управления не совпадает с потоком зависимостей. Вызов идёт вперёд, а знание — назад.

Работу по-прежнему делает stripe. Но теперь про контракт знает он, а не наоборот.

В коде это три файла. Первый — мой модуль, у него больше нет ни одного импорта:

// features/checkout/model.ts
export type PaymentGateway = {                       // контракт: что мне нужно
  charge(input: { orderId: string; amount: number }): Promise<{ ok: boolean }>;
};

export function createCheckout({ gateway }: { gateway: PaymentGateway }) {
  return {
    pay: (orderId: string, amount: number) => gateway.charge({ orderId, amount }),
  };
}
Фабрика — функция, которая сама работу не делает, а собирает и возвращает того, кто будет делать. createCheckout — фабрика: ей дают зависимость, она отдаёт готовый checkout.

Второй файл — stripe, он вообще не меняется, он про нас не знает. Третий — место сборки:

// app/composition.ts — единственное место, где живёт конкретика
import { createCheckout } from '@/features/checkout';
import { stripe } from '@/shared/api/stripe';

export const checkout = createCheckout({
  gateway: {                                          // ← адаптер, целиком
    charge: ({ orderId, amount }) =>
      stripe.charge({ order: orderId, sum: amount, cur: 'KZT' }),
  },
});
Адаптер — прослойка, переводящая один формат в другой. Здесь это одна стрелочная функция: снаружи она выглядит как charge из контракта, внутри зовёт stripe с его собственными именами полей.

Обрати внимание: нигде нет ни class, ни слова implements. TypeScript сверяет по форме — если объект похож на PaymentGateway, значит, он им и является. Это называется структурная типизация, и благодаря ей инверсия во фронте почти не требует лишнего кода.

Детектор: один вопрос на всё

Где объявлен тип зависимости?

  • У того, кто её использует — инверсия есть.
  • У того, кто её реализует — инверсии нет, как бы красиво ни назывались слои.
Задание 3 — главное в уроке

Инверсия здесь есть?

import { stripe } from '@/shared/api/stripe';

export function pay(orderId, amount) {
  return stripe.charge({ order: orderId, sum: amount, cur: 'KZT' });
}
  • Да, ведь модуль вызывает чужой код
  • Нет, модуль знает про stripe напрямую
  • Инъекция есть, а инверсии нет

5. Три похожих термина

Вот здесь и сыплются на собеседовании: три названия, которые звучат почти одинаково, но находятся на разных этажах.

Инверсия отвечает на вопрос «кто кого знает». Инъекция — на вопрос «как передали».

Задание 4 — соедини пары

Нажми термин слева, потом его описание справа.

  • Принцип: зависеть надо от абстракций, а не от реализаций
  • Приём: стрелка знания смотрит против стрелки вызова
  • Механизм: зависимость передали снаружи, а не взяли импортом
  • Описание формы зависимости, записанное типом
  • Прослойка, переводящая чужой формат в нужный

6. Ловушка: инъекция без инверсии

Это самый частый способ выглядеть архитектурно и не получить ничего.

Задание 5

Зависимость передали аргументом. Инверсия произошла?

import type { TelegramClient } from '@/shared/telegram';

export function notify(client: TelegramClient, text: string) {
  return client.send(text);
}
  • Да, зависимость же передаётся снаружи
  • Нет, тип объявлен на стороне телеграма
  • Нет, потому что нет и инъекции
Чтобы починить, достаточно объявить свой тип у себя: type Sender = { send(text: string): Promise<void> } — и телеграм подстроится под него.

7. Фасад — это ещё не инверсия

Фасад — обёртка, которая прячет сложность чего-то большого за простым набором функций. Полезная штука, но к инверсии отношения не имеет.

Самое частое возражение звучит так: «у нас всё завёрнуто в сервисы, у нас уже абстракция». Смотри, что на самом деле происходит:

Транзитивная зависимость — зависимость через посредника. userStore не знает про httpClient напрямую, но зависит от него через userApi: цепочку не разорвать, изменение всё равно доедет.
Задание 6

Почему фасада недостаточно, если цель — оторвать модуль от чужой изменчивости?

  • Зависимость осталась транзитивной, а тип объявляет не потребитель
  • Фасад делает код сложнее и добавляет лишние вызовы
  • Фасады не поддерживаются структурной типизацией
Это не значит, что фасады плохие. Просто фасад решает задачу «спрятать сложность», а не задачу «развернуть зависимость».

8. Ты делал это каждый день — просто в React

А теперь приятное. Половина приёмов из этого урока у тебя уже в руках.

Колбэк-проп — функция, переданная компоненту пропом. Компонент её вызывает, но не знает, что она делает. onClick — самый обычный пример.
Слот — проп, в который передают готовую разметку (тип ReactNode), а компонент просто вставляет её у себя. children — это тоже слот.
Render prop — проп-функция, которая возвращает разметку. Компонент решает, где и сколько раз её вызвать, но не решает, что именно нарисуется. 
// ❌ карточка знает про кнопку, кнопка знает про стор, стор знает про API
function TaskCard({ task }) {
  return <div>{task.title}<DeleteTaskButton id={task.id} /></div>;
}

// ✅ карточка не зависит ни от чего, кроме своих пропсов
function TaskCard({ task, actions }: { task: Task; actions?: ReactNode }) {
  return <div>{task.title}{actions}</div>;
}

// собирают их уровнем выше
<TaskCard task={task} actions={<DeleteButton onClick={() => remove(task.id)} />} />

Побочный эффект — дерево компонентов становится плоским:

Глубина вложенности — хороший индикатор: чем глубже, тем больше компонент знает о чужих внутренностях.

Задание 7

В FSD сущность order должна показать кнопку «отменить заказ», но кнопка — это фича, и импорт из сущности в фичу запрещён. Что делать?

  • Импортировать кнопку напрямую и отключить правило линтера
  • Сущность объявляет слот, кнопку кладёт виджет сверху
  • Перенести кнопку внутрь сущности, раз она там нужна

9. Context: когда это DI, а когда глобальная переменная

React Context по назначению — не хранилище состояния, а способ доставки зависимости: возможность пользоваться контрактом до того, как где-то наверху подставили реализацию. Так устроены все инфраструктурные библиотеки:

  • useQuery работает с абстрактным QueryClient, конкретный приезжает в <QueryClientProvider>;
  • useNavigate не знает, роутер тут history, hash или memory;
  • useSelector не знает, из каких редьюсеров собран стор.

Заметь, в чью пользу здесь инверсия: это библиотека защищена от твоего кода, а не твой код от библиотеки.

Задание 8

По какому признаку отличить контекст-инверсию от контекста-глобальной-переменной?

  • По количеству: один контекст на приложение — плохо, много — хорошо
  • По тому, лежит ли реализация рядом с объявлением контекста
  • По тому, используется ли useContext или useSyncExternalStore
И ещё: контекст декларативен — не обернул в провайдер, получил ошибку сразу и в понятном месте. Этим он отличается от сервис-локатора, который надо наполнять вручную и который падает неожиданно.

10. Композиционный корень

Если конкретика исчезла из модулей, значит, она куда-то переехала. Переехала она наверх.

Композиционный корень (composition root) — единственное место, где абстрактное встречается с конкретным: app/, main.tsx, провайдеры, composition.ts.

Правило движения: конкретика течёт вверх, абстракции — вниз. Толстый app — это не запах, это признак того, что всё сработало.

11. Где здесь SOLID

Теперь можно вернуться к аббревиатуре — на подготовленную почву. SOLID придуман около 2000 года для языков с классами и наследованием. Дословно во фронт он не переносится, но три буквы из пяти работают отлично.

D — то, чем мы занимались весь урок

Dependency Inversion Principle: зависеть надо от абстракций, а не от реализаций. Это буква D. Всё, ты её уже знаешь.

S — одна причина для изменения

Формулировка «модуль должен делать одну вещь» бесполезна: «одна вещь» — резиновое понятие. Рабочая формулировка другая: у модуля должна быть ровно одна причина измениться, то есть ровно один заказчик правок.

function OrderCard({ order }) {
  const money = new Intl.NumberFormat('kk-KZ', { ... }).format(order.total); // финансы
  const canRefund = user.roles.includes('admin');                            // безопасность
  const { data } = useQuery(['order', order.id], () => api.get(...));        // бэкенд
  return ...;                                                                // дизайн
}
Задание 9

Сколько причин для изменения у этого компонента?

  • Одна — он же рисует одну карточку заказа
  • Четыре — по числу разных команд-заказчиков
  • Столько, сколько строк в компоненте

O — расширяем, не трогая

// ❌ каждый новый случай = правка самого Modal
<Modal mode="edit" | "view" | "compact" | "danger" />

// ✅ Modal не меняется никогда, меняется то, что в него кладут
<Modal header={<EditTitle />} footer={<SaveButton />}>{form}</Modal>

Первый вариант — это то самое control coupling из первого урока: снаружи флагом дёргают ветвление внутри. Второй — слот, то есть снова инверсия.

L и I — по одной честной фразе

БукваЧто говорить
L — ЛисковБез наследования во фронте почти не встречается. Живёт как «не ломай контракт при расширении»: если IconButton — обёртка над Button, она обязана принимать всё то же и вести себя так же.
I — разделение интерфейсовНе заставляй потребителя знать о том, чем он не пользуется: не проси весь объект user, если нужен только userId. Толстые контексты — это же нарушение, и оно ещё и ререндеры даёт.

12. Чем за это платят

Как и в первом уроке: любое решение — сделка, и обе стороны надо уметь назвать вслух.

Что дешевеетЧем платим
Замена реализации: платёжка, транспорт, хранилищеКосвенность: чтобы понять, что реально вызовется, надо идти в композиционный корень
Тесты без моков — подставил фейк и всёБольше кода: контракт, фабрика, адаптер вместо одного импорта
Модуль можно физически вынуть и переиспользовать«Перейти к определению» ведёт в тип, а не в рабочий код
Запрещённые по слоям связи разрываются без хаковНовому человеку в команде дольше вникать
Когда инвертировать НЕ надо
  • Чистые утилиты. formatDate, clamp — у них нечему меняться, разворачивать нечего.
  • Одна реализация, и она стабильна. Инверсия «на будущее» — ставка на угаданное будущее, а первый урок был ровно о том, что угадывать не надо.
  • Внутри одного модуля. Инверсия — инструмент для границ, не для внутренностей.

Рабочее правило: инвертируй там, где начинается чужая изменчивость — сеть, хранилище, платежи, аналитика, время и Math.random — и там, где связь запрещена правилами слоёв.

13. Как это звучит на собеседовании

Скрипт на 40 секунд

«Инъекция — это как передали: аргументом, пропом, через контекст. Инверсия — это кто кого знает: контракт объявляет тот, кто зависимостью пользуется, а реализация подстраивается под него и подставляется в композиционном корне. Проверяется одним вопросом: если тип импортирован из модуля-реализации — инверсии нет, сколько бы слоёв ни было построено. В React для этого обычно не нужны даже интерфейсы: слот, render prop и колбэк-проп — уже инверсия, потому что вызов идёт вниз, а зависимости вниз нет.»

Чего не делать
  • Не называть «внедрением зависимостей» всё, что принимает аргументы. Уточняй, чей тип.
  • Не называть фасад инверсией — транзитивная зависимость никуда не делась.
  • Не предлагать DI-контейнер в React-проекте: это инструмент мира классов и интерфейсов.
  • Не пересказывать SOLID по буквам. Скажи, какие три работают во фронте и как выглядят в коде.

Шпаргалка

  • Зависимость — чужой код, без которого мой не работает. Видна по import.
  • Контракт — форма зависимости без содержимого. В TS это type.
  • Две стрелки: поток управления — кто кого вызывает; поток зависимостей — кто про кого знает.
  • Инверсия = эти две стрелки смотрят в разные стороны.
  • Инъекция = механизм доставки: аргумент, проп, контекст, контейнер.
  • DIP = принцип (зачем), инверсия = приём (что делаем), инъекция = механизм (как передали).
  • Детектор: где объявлен тип? У потребителя — инверсия есть. У реализации — нет.
  • Инъекция без инверсии — самая частая подделка: чужой тип в сигнатуре.
  • Фасад ≠ инверсия: зависимость остаётся транзитивной.
  • В TS не нужен implements — работает структурная типизация, адаптер часто в одну стрелку.
  • Слот, render prop, колбэк-проп — инверсия, которой ты пользуешься каждый день.
  • Context — доставка зависимости, а не хранилище состояния.
  • Композиционный корень — единственное место встречи абстрактного и конкретного. Толстый app — это норма.
  • Не инвертируй чистые утилиты, стабильную единственную реализацию и внутренности модуля.

Первоисточник

  • Kent C. Dodds, «Inversion of Control» — kentcdodds.com/blog/inversion-of-control. Лучший разбор темы для React-разработчика: одна и та же функция рефакторится шаг за шагом. Двадцать минут чтения.
  • Robert C. Martin, «Clean Architecture», главы 8 и 11 — откуда взялись формулировки OCP и DIP, включая «поток управления против потока зависимостей».
  • Урок 2 курса Паромова (docs/paromov-lessons/2.md) — та же тема на классах, функциях, контексте и компонентах.

Объясни разницу между инверсией и инъекцией так, будто напротив сидит интервьюер. Сформулируй вслух целиком, потом сверься.

Инъекция — механизм доставки: зависимость передали снаружи, а не взяли импортом. Инверсия — направление знания: контракт объявляет потребитель, реализация подстраивается. Инъекция без инверсии бывает и ничего не даёт: если тип пришёл из чужого модуля, стрелка не развернулась. Проверка — один вопрос: где объявлен тип.

Разбор упражнения 02

Упражнение practice/02-di-notifications — та же идея, но руками. Было так: модуль уведомлений намертво привязан к телеграму.

// src/notifications/notify.ts — стартовое состояние
import { sendTelegram } from '../transport/telegram.ts';   // ← вся проблема в этой строке

export async function notifyUser(n: Notification): Promise<void> {
  await sendTelegram(n.userId, n.text);
}

Из пяти тестов четыре красные. Но по делу говорит только один:

not ok 2 — модуль notifications не знает о транспорте
  актуально: [ 'transport' ]
  ожидалось: []

Остальные три падают следом, потому что фабрики ещё нет. Чинится всё одним движением в двух файлах.

Шаг 1. Объявить контракт у себя

Импорт удаляем и вместо него описываем, что нам нужно от транспорта:

// src/notifications/notify.ts — ни одного импорта
export type Transport = {
  send(userId: string, text: string): Promise<void>;
};

Это тот самый разворот стрелки. Раньше форму диктовал телеграм, и мы под неё подстраивались. Теперь форму диктуем мы, и подстраиваться под неё будет он.

Ловушка, на которой теряют полчаса

Соблазн написать так:

import type { Sent } from '../transport/telegram.ts';   // ❌ тест останется красным

В рантайме такой импорт исчезает — но тест №2 смотрит не на рантайм, а на текст файла, и видит строку from '../transport/…'. И он прав: если тип пришёл со стороны реализации, стрелка знания не развернулась. Тип обязан родиться у потребителя.

Шаг 2. Превратить функции в фабрику

Функции больше не могут висеть сами по себе: им нужен транспорт, а взять его неоткуда, кроме как снаружи. Значит, их надо создавать вокруг переданной зависимости:

export function createNotifier({ transport }: { transport: Transport }) {
  async function notifyUser(n: Notification): Promise<void> {
    await transport.send(n.userId, n.text);
  }

  async function notifyAll(users: string[], text: string): Promise<void> {
    for (const userId of users) {
      await notifyUser({ userId, text });   // ← через свой же notifyUser, а не мимо
    }
  }

  return { notifyUser, notifyAll };
}

Обрати внимание на notifyAll: он зовёт свой notifyUser, который сидит в том же замыкании и держит подставленный транспорт. Если бы он ходил к транспорту напрямую или к какому-то внешнему notifyUser, тест №5 остался бы красным. Замыкание здесь работает ровно как конструктор класса — приватное поле transport, только без слова class.

Шаг 3. Связать в композиционном корне

// src/app/composition.ts
import { createNotifier } from '../notifications/notify.ts';
import { sendTelegram } from '../transport/telegram.ts';

export const notifier = createNotifier({
  transport: { send: sendTelegram },      // ← адаптер целиком, одна строка
});

Вот и весь адаптер: { send: sendTelegram }. Ни class, ни implements — TypeScript просто сверил, что sendTelegram принимает два стринга и возвращает Promise<void>, то есть подходит под Transport по форме. Это структурная типизация в действии.

Заметь и другое: оба импорта переехали сюда. Конкретика не исчезла, она поднялась наверх — ровно то движение, о котором был раздел про композиционный корень.

Что позеленело и почему

Посмотри, что он делает: подставляет фейковый транспорт и проверяет, что настоящий outbox остался пустым. Это юнит-тест без единого мока, без jest.mock, без перехвата сети — просто другой аргумент. Именно это стоит рассказывать на собесе, когда спрашивают «как вы тестируете бизнес-логику».
